小さな機能を一つ作るとき、最初に決めるのは完成した見た目ではなく、どんな順番で手が動くかだ。ボタンを押し、画面が変わり、保存して戻る。その短い往復が自然なら、細かな装飾はあとから考えられる。

今回試したのは、記事を先に作ってから編集する流れだった。「新規記事」を押すと下書きが保存され、変わらない ULID が一つ付く。画面が移った時点で、編集する相手はすでに存在している。

## 先に作る理由

空の編集画面で書き始め、最後に初めて記事を作る方法もある。けれども画像や下書きの続きを扱うなら、最初から保存先が決まっている方が分かりやすい。公開名を後で変えても、内部の ID は変えない。

```ts 記事作成の流れ
const id = createUlid();
await db.prepare(
  "INSERT INTO posts (id, status, title) VALUES (?, 'draft', ?)"
).bind(id, "無題").run();

return redirect(`/blog/${id}?edit=1`);
```

これは流れを説明するための短い擬似コードで、実際には日付や本文の初期値も保存する。大切なのは、編集画面が **既存の一件** を開いているという点だ。

| 操作 | D1 の状態 | 画面 |
| --- | --- | --- |
| 新規記事を押す | 下書きと ULID を作成 | 編集を開始 |
| 完了を押す | 同じ ID の本文を更新 | 記事を表示 |
| エイリアスを付ける | 公開名だけを更新 | 正規 URL へ移動 |

### 名前を変えても道を残す

記事の URL を短くするため、あとから `small-experiment` のようなエイリアスを付けられる。古い ULID の URL を知っている人にも届くように、元の道は正規 URL へ転送する。

```text URL の変化
/blog/01M368BXFC6Q0BWDG5QX8MSKPC
        ↓ 308
/blog/small-experiment
```

ここで「一つの ID が、いくつの公開名を持てるか」を考える。現在の名前は一つでも、過去に使った名前は残してよい。正規 URL の数を $C$、保存した別名の数を $A$ と書けば、記事一件について $C=1$ のまま $A$ は増やせる。

$$
C=1,\qquad A\geq 0
$$

> [!NOTE ローカルでの確認]
> この試作では認証をまだ接続していない。書き込みの流れを確かめる間だけ、ローカル環境で操作を許可している。

## 失敗したときの戻り道

手順を確かめるときは、成功した画面だけでなく失敗したときの戻り方も見る。タイトルを空のまま保存しようとした場合、入力が消えずに編集を続けられることが必要だ。

たとえば保存処理を一度止め、題名だけ直して再び「完了」を押す。最初に作った ULID が残っていれば、同じ記事に戻って来たと分かる。書きかけの本文まで消えてしまったら、エラー表示が丁寧でも操作としては足りない。

SQL の形にすると、保存は新しい行の追加ではなく、既存行の更新になる。公開名は別の欄なので、本文を直すたびに URL を変える必要はない。

```sql 同じ記事を更新
UPDATE posts
SET title = ?, body_markdown = ?
WHERE id = ?;
```

- [x] 新規作成後に編集画面へ進む
- [x] 保存後に同じ記事を読み直せる
- [x] エイリアスから記事を開ける
- [ ] 認証したユーザーだけに編集を許す

:::details{summary="次に試したいこと"}
一覧の見た目を決める前に、公開と下書きの並べ方、長い題名の扱い、削除の確認方法をもう一度試す。操作が固まってから装飾を考えたい。
:::

## 一覧に戻るまで

記事を保存して終わりではない。もう一度一覧を開き、先ほど直した題名と状態が見えるところまでが一つの操作だ。編集画面だけに成功の印が出ても、一覧が古いままなら「本当に保存されたのか」と迷う。

削除も同じで、押し間違いを防ぐ確認と、消した後に一覧へ戻る道が要る。確認を長い説明にする必要はない。対象の記事名を見せ、もう一度だけ操作を選べるようにする。

```text 操作の往復
一覧 → 新規作成 → 編集 → 保存 → 記事 → 一覧
一覧 → 削除確認 → 削除 → 一覧
```

この往復を確かめてから、日付やカテゴリの並べ方を試す。機能の数を増やす前に、今ある一往復が途切れないことを見ておきたい。
